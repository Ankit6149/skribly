Development notes

Public downloads are disabled. These notes separate implemented foundations from open release gates and deferred capabilities.

Implemented foundations

  • A compact typed-note editor opened with Ctrl + Shift + Space.
  • Fail-closed foreground target capture and process/window revalidation.
  • Deterministic native create-versus-reopen requests.
  • Ordered local saves with dirty, saving, saved, failed, and retry states.
  • Crash-safe schema-v3 local storage with schema-v1/v2 migration and recovery generations.
  • A normal non-floating All Skribs window for active-note and Trash search, reading, and versioned JSON export.
  • Reversible 30-day local Trash, same-record restore, and separately confirmed permanent deletion.
  • Target-monitor work-area placement, bounded Windows event delivery, and single-instance routing.
  • A visible first-run guide and reopenable Quick guide in the tray.

The exact current workflow

  1. Focus a supported Windows application.
  2. Press Ctrl + Shift + Space.
  3. Skribli creates or reopens the deterministic contextual note.
  4. Write in the compact editor.
  5. Choose Done, Escape, Ctrl+Enter, or close.
  6. Skribli waits for the latest non-empty draft to save, then fully hides the editor.
  7. Choose Delete only when needed; the note moves to local Trash and can be restored from All Skribs.

The current MVP leaves no floating dot, attached tab, checklist, permanent toolbar, saved-notes widget, or full-screen interactive overlay.

Trash behavior in this release candidate

  • Active notes and Trash are separate searchable views.
  • Trashed notes cannot reopen through the shortcut or be edited in place.
  • Restore preserves the original note ID, content, and stored context.
  • Permanent deletion is available only inside Trash after note-specific confirmation.
  • Expired or invalid Trash records remain visible for review; this release does not silently purge them.
  • Read-only users retain read and export access to active and trashed records.

Open release gates

  • Add portable import with preview, duplicate handling, migration, and rollback.
  • Define and validate automatic purge, configurable retention, archive, and attachment cleanup.
  • Complete context-safe open-in-application and re-anchor decisions without guessing targets.
  • Finish installer build, install, upgrade, repair, uninstall, and rollback validation.
  • Run the physical Windows matrix across display scaling, lifecycle interruptions, suspend/resume, Remote Desktop, and long sessions.
  • Reconcile support, compatibility, checksums, signing, and download delivery with the exact candidate.

Why downloads remain disabled

A build is not ready for customers merely because it compiles. Installer access will reopen only after the exact Windows candidate has reproducible packaging, complete automated gates, physical runtime evidence, a known-limitations record, and customer-facing copy that matches the binary.
