Repository-grounded audit · baseline a3f5b3a · v0.1.24

The engineering is becoming richer faster than the interaction hierarchy can absorb it.

Skribli is no longer a simple sticky note. The current desktop product has context capture, local-first recovery, rich text, ink, attachments, reminders/repeats, task/archive behavior, manual resizing, a persistent Rail, a full local Library, account/trial enforcement and return-to-context flows. The redesign problem is not “make this prettier.” It is deciding what deserves to exist at rest, what appears after intent, and what belongs somewhere else entirely.

02 · audit correction log

What the deeper code pass corrected.

This section exists so the design record distinguishes implementation truth from earlier conceptual assumptions.

Important correction: task completion is not a normal-footer peer today.

Current code: the normal footer presents a save state, Trash, and Done. The Complete task action appears inside the delete-confirmation branch alongside Cancel and Move to Trash. That coupling is real and should be audited as an interaction anomaly—not described as a permanently visible footer button.

Design implication: task semantics still need clarification, but the immediate issue is not “remove Complete from the normal footer.” It is “decide when a Skrib becomes actionable, then place completion in the correct state rather than attaching it to deletion confirmation.”

Command bar correction

Current visible command-bar peers are Draw, Reminder, Text size and Surface size. Colour lives in the header. Attachments are integrated into the editor/attachment panel instead of being another permanent command-bar icon.

Expansion correction

Drawing forces Large. Reminder expands Compact→Medium. The attachment drawer expands Compact→Medium. These automatic size transitions already exist and should be refined, not reinvented from scratch.

Done correction

For a normal contextual note, Done safely saves and collapses back to the Rail. A detached/open-here note closes instead. Empty notes are discarded only when they have no persisted rich extras.

03 · current runtime truth

Design from what the app actually guarantees.

These are product behaviors the future UI must either preserve explicitly or change intentionally.

Fresh shortcut creation

Ctrl + Shift + Space creates a new contextual Skrib after foreground validation; existing notes are reopened from retrieval surfaces.

Save is fail-closed

Done/close can be blocked by failed text, ink, attachment or reminder persistence. The editor stays open rather than pretending success.

One active editor

Note switching waits for current note persistence. The product is deliberately not a multi-floating-window canvas.

Rich content is one note

Text, rich formatting, ink, files and reminder data are coordinated under one Skrib identity.

Local content / remote entitlement split

Account and trial state can block writes, but signing in does not upload Skrib content.

Context return is bounded

Skribli can return toward saved applications/windows and can start allowlisted apps, but exact closed URLs, folders or DOM positions are not guaranteed.

Rail has two navigation axes

Here/All/Archive is one axis; application/context group selection is another. Both appear before the note rows.

Library mixes retrieval and administration

Search/reading share the same surface with Refresh, Import, Export, Archive, Trash and permanent-delete recovery.

Four resize corner buttons exist

The native resize hit targets are explicit DOM buttons at all four corners. Future design can preserve access while lowering visual salience.

04 · future design contract

Rules before production UI is redrawn.

Visual polish cannot compensate for the wrong information architecture.

Zero management tax

Context should organize by default. Users should not need a maintenance ritual to keep Skribli useful.

Quiet until intention

Resting UI shows only the current job. Rich capability appears after a meaningful gesture or mode change.

Physical content, precise shell

Skribs/media can feel tactile. Navigation, focus, error handling and layout stay exact.

Persistent UI earns every pixel

Anything that remains on the desktop must be hideable, recoverable and extremely low-noise.

Skrib anatomy: the real clutter is distributed across four regions.

The note should not be judged as “toolbar clutter” alone. Header, command bar, canvas/attachments and lifecycle/footer all compete.

Header has three jobs P0

Place/context identity, paper colour, window positioning and close/save behavior all meet in one shallow strip. Future context-management controls must not be added here as more peer icons.

Command bar is already at its extensibility limit P0

Draw, Reminder, Text size and Surface size are reasonable individually, but future checks/arrows/shapes/pins/labels cannot become five more peers.

Attachments are not a toolbar problem corrected

Attachment actions are integrated through the editor and attachment panel. The redesign should preserve that contextual behavior rather than adding an Attach icon merely for symmetry.

Resize has two models P1

Surface-size presets and four manual corner hit targets coexist. Keep direct manipulation, but decide what the preset actually means once free resize is first-class.

Save blocking is a strength protect

Rich-content saving can keep the note open. Future UI should make this feel calm, not weaken the safety contract.

Task-completion coupling to delete confirmation

The current delete-confirmation branch includes a Complete-task action beside Cancel and Move to Trash. This is semantically unusual: “I want to delete” should not be the route through which task completion becomes discoverable. The future model should decide task identity earlier and expose completion only when the note is genuinely actionable.

Two permanent filtering dimensions P0

Here/All/Archive plus application-group filtering means users parse navigation before thought content.

Manual Refresh is redundant in the happy path P1

The Rail already refreshes from several events. Keep manual refresh as recovery/debug affordance, not a prominent trust mechanism.

13 · cross-surface journeys

The product should be designed as transitions, not isolated screens.

Many of Skribli's most important UX qualities live between surfaces.

Capture → disappear

The fastest successful loop.

work→shortcut→fresh Skrib→write→Done→Rail
Retrieve here

Read/edit an existing thought without changing its saved anchor.

Rail/Find→Open here→detached editor→save/close
Return there

Attempt the saved application/context honestly.

Rail/Find→Return ↗→OpeningJourney→match/start/fallback
Bring back later

Reminder should feel like temporal resurfacing, not task conversion.

Skrib→Bring back→notification→Open / Return / Later
Complete something

Only explicit actionable Skribs should enter this lifecycle.

actionable note→Complete→Archive/Past→restore if needed
Recover safely

Failure must preserve user confidence in local data.

save/storage failure→stay open/read-only→retry/export/diagnostics→verified safe state
14 · future pressure

Design for the next capabilities without advertising them all at once.

The future architecture must absorb growth without recreating a ribbon, dashboard or file manager.

Structured marks

Checks, arrows, shapes, pins and labels should extend one Mark system. Object selection swaps properties contextually; it does not add another permanent toolbar.

Richer context

Browser/file precision, confidence and rules need an Inspector/repair layer. Healthy context remains a small human place label.

More platforms / sync

macOS parity or optional sync should not change the local-first mental model. Device/account/sync health belongs in Control, not inside the thought.

15 · execution sequence

Redesign in dependency order, not by whichever screen looks worst.

This avoids polishing a surface whose information architecture will immediately change.

1 · Semantic decisions

Reminder vs task, Done vs Complete, Open here vs Return, Active/Past/Trash, what “size” means, and what persistent Rail presence is allowed to do.

2 · P0 interaction systems

Resting/heavy Skrib, tool gateway, Rail presence/expanded Rail, Home/Find shell, context repair and save/recovery.

3 · Object language

Attachments, reminder/time objects, drawing/structured marks, calendar dates, micro-components, hover/focus and motion.

4 · Production migration

Move approved primitives into React/Tauri surface-by-surface with keyboard, DPI, reduced-motion, failure-state and real native-window acceptance.
